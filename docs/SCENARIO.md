# 场景文档：实时 AIOps 事件分流与处置 Copilot（面向生产运维）

> 目标：找到“真正适合 Kafka/Flink + RAG + vLLM + OTel + K8s + Chaos”的落地场景，而不是为了用技术而用技术。

---

## 1. 为什么选择这个场景（匹配技术栈的原因）

这个场景的核心不是“做一个会聊天的运维机器人”，而是把 **生产运维的事件流**（告警、日志、变更、工单）做成一个 **实时 AI 数据系统**：

- **天然是流式数据**：告警/日志/Trace 是持续不断的事件流，且高并发、高峰值，适合 Kafka 作为总线、Flink 做实时处理。
- **强时效**：MTTA/MTTR 直接影响业务损失，要求分钟甚至秒级的分流与归因；离线跑索引/手工查资料不够。
- **知识持续变化**：Runbook、SOP、架构拓扑、历史事故复盘都在变；需要“实时更新的 RAG”，而不是每天离线重建。
- **需要生产级可观测**：一次“AI 误判”会带来错误处置；必须能用 OTel 追踪每一步耗时/命中证据/模型调用。
- **必须具备韧性与降级**：模型挂了、向量库慢了、外部依赖超时都不能拖垮告警链路；Chaos 与降级路径是必需品。
- **推理吞吐有成本压力**：事件高峰时并发很高；vLLM 的连续批处理与 KV cache 管理能明显改善吞吐/成本比。

一句话：**这不是“AI 应用”，而是“AI 事件处理系统”**，对你已有的实时/平台/基础设施能力复用度最高。

---

## 2. 业务背景与痛点（问题定义）

典型中大型互联网/企业 IT 运维链路里，日常会遇到：

- 告警噪音：同一故障触发大量重复/相关告警（告警风暴），值班同学先被“噪音淹没”。
- 定位耗时：需要跨系统查日志、Trace、变更记录、拓扑信息，再对照 runbook；新人更慢。
- 处置不一致：不同人对同一类故障处理路径不一致；复盘资料难以被持续复用。
- 观测割裂：Prometheus 指标、日志平台、APM、工单系统彼此独立，缺少“事件级”的统一视图。
- 事故后才总结：复盘沉淀（RCA、runbook 更新）与在线系统脱节，难以实时反馈到后续事件处置。

因此，需要一个系统把“事件->信息聚合->建议->执行->反馈”闭环做起来。

---

## 3. 目标用户与使用边界

**目标用户**

- 一线值班 SRE/运维工程师：需要快速分流、给出下一步排查动作。
- 业务研发 Oncall：希望拿到“最小可用上下文”，减少反复追问。
- 运维负责人：关心 MTTA/MTTR、告警质量、团队一致性与成本。

**非目标（本阶段不做）**

- 自动执行高风险动作（如直接重启核心集群/删库改表）。系统可以“建议 + 提示风险”，但默认不自动执行。
- 替代现有监控/日志平台：系统只做汇聚、增强与联动，不重造可观测三件套。

## 4. 端到端“详细场景”描述（一个具体事故的处理链路）

### 4.1 触发：告警风暴（实时流入口）

某电商活动期间（峰值流量），Prometheus 报警：

- `checkout-service` p95 延迟从 200ms 升至 2.5s（持续 2 分钟）
- `mysql-order` 连接数异常攀升
- `k8s` HPA 频繁扩缩容

这些告警进入 Kafka `alerts` 主题（同一事故在 30 秒内可能产生数百条告警）。

### 4.2 Flink 实时聚合：去重、关联、构建“事件包”（Event Envelope）

Flink Job 以 1~2 分钟滑动窗口做：

- 去重/合并：相同告警指纹合并，保留计数与最新样本
- 关联：根据服务拓扑（CMDB/服务地图）把相关服务/依赖合并进一个 “Incident Candidate”
- 补全上下文：拉取近 10 分钟的关键指标摘要（p95、错误率、QPS、饱和度）、最近变更（发布/配置）摘要

输出一个结构化事件包（JSON），写入 Kafka `incident_candidates` 主题，并存一份到 OLAP（便于复盘与分析）。

### 4.3 LLM 作为“流式算子”：分流与初步归因

Flink 调用内部 LLM Gateway（背后由 vLLM 提供推理）做两类轻量任务：

1) **事件分类与优先级**：P0/P1/P2，支付链路优先；判断是否可能是告警风暴/误报
2) **归因假设**：如“下游数据库连接耗尽导致线程池排队”，并给出“证据点列表”

> 注意：这里不是让模型凭空猜，而是让它在结构化上下文里做“归纳与下一步建议”，且每条建议必须引用证据字段（指标、日志片段、变更记录等）。

### 4.4 实时 RAG：检索 runbook、相似事故、处置步骤（并保持“最新”）

系统对事件包进行检索：

- 从向量库检索：
  - `runbook`：针对 “支付延迟/数据库连接耗尽” 的 SOP
  - `postmortem`：历史相似事故与根因
  - `known-issues`：最近一周新出现的问题与临时 workaround

并使用 rerank（可用轻量模型/规则）提高相关性，最终构建 “Evidence Pack”（可引用证据包）。

**为什么要实时更新 RAG？**

- 新事故复盘、新增 workaround、配置变更会持续产生新文档
- 如果依赖“每日离线建索引”，值班同学在当天最需要知识时拿不到

因此用 Kafka + Flink 把新增/变更文档实时做：

`清洗 -> 分块 -> embedding -> 写入向量库 -> 版本化/可回滚`

### 4.5 输出：工单联动 + 可操作的建议（不是“泛泛总结”）

系统将结果写入工单系统（如 Jira/ServiceNow/自研）：

- 标题：`[P0] checkout-service 延迟飙升（疑似 mysql-order 连接耗尽）`
- 摘要：3~5 行（发生时间、影响范围、关键指标）
- 证据：命中指标/变更/日志片段（可点击回到原系统）
- 建议处置（按优先级）：
  1. 检查 `mysql-order` 连接池上限与慢查询（附 runbook 链接）
  2. 回滚最近 15 分钟内 `checkout-service` 的配置变更（若存在）
  3. 临时限流/降级开关建议（标注风险与影响）

并在 IM/Oncall 渠道（企业微信/Slack）推送一条“事件卡片”（只推送关键信息，避免制造噪音）。

### 4.6 反馈闭环：处置结果回流，驱动评估与知识更新

当值班同学标记工单状态/填写根因：

- 回流 Kafka `incident_outcomes` 主题
- 用于：
  - 模型效果评估（是否命中根因、建议是否可执行）
  - 自动收集 bad case（用于 prompt/检索/规则改进）
  - 触发 runbook/复盘文档更新提醒（人审后入库）

## 5. 系统架构（组件与职责）

```
数据源(监控/日志/APM/变更/工单)
  -> Kafka(事件总线)
      -> Flink(实时聚合/特征/清洗)
          -> LLM Gateway
              -> vLLM(推理服务)
          -> RAG(向量检索 + rerank)
          -> 输出(工单/IM/仪表盘)

全链路观测：OpenTelemetry Trace + Metrics + Logs
韧性：降级/熔断/重试 + Chaos 演练
部署：K8s（弹性、灰度、多模型）
```

### 5.1 Kafka（事件总线）

- 主题建议：
  - `alerts`（原始告警）
  - `logs_samples`（抽样日志片段/统计摘要）
  - `changes`（发布/配置变更）
  - `incident_candidates`（聚合后的事件包）
  - `rag_docs`（runbook/复盘/公告等文档变更流）
  - `incident_outcomes`（处置结果回流）

### 5.2 Flink（实时处理层）

- 窗口聚合（滑动/会话窗口）做事件合并
- 规则 + 轻量特征（统计/阈值）把 “噪音” 在调用 LLM 前过滤掉
- 对 LLM 调用做限速/超时/回退策略，避免事故高峰把推理服务打爆

### 5.3 vLLM（推理层）

定位：**高并发、低成本的内部推理服务**，为“分类/摘要/建议”等高频任务提供吞吐。

- 支持 OpenAI 兼容接口，便于统一接入网关
- 结合连续批处理提升峰值期并发能力

### 5.4 RAG（知识增强）

- 文档类型：
  - Runbook/SOP（强结构、强可执行）
  - Postmortem/RCA（经验与模式）
  - Known Issues / 公告（短期 workaround）
- 关键要求：
  - 实时入库、可版本化、可回滚
  - 引用必须可追溯（每条建议能追到“引用的文档 chunk”）

### 5.5 OpenTelemetry（全链路可观测）

每一次事件处理都记录：

- Flink 聚合耗时、入/出 Kafka 延迟
- 检索耗时、命中率、topK 分布
- LLM 调用耗时、token、失败率、重试次数
- 输出落地耗时（工单/IM）

目标是能回答：

- “慢在哪里？”、“贵在哪里？”、“错在哪里？”、“证据来自哪里？”

### 5.6 Chaos（韧性演练）

建议演练故障：

- vLLM 服务不可用/延迟增加：是否自动降级为“规则引擎 + 历史模板”
- 向量库延迟：是否降级为关键字检索/固定 runbook
- Kafka 分区抖动：是否出现重复/乱序处理，是否有幂等保障

## 6. 关键设计原则（保证“可落地”）

1) **先结构化再生成**：尽量让 Flink 把上下文变成结构化事实（指标摘要、变更清单、依赖拓扑），LLM 做“归纳与建议”。
2) **证据优先**：每条输出必须带可追溯证据（指标/日志/文档 chunk），没有证据就降低置信度或不输出。
3) **先过滤后调用**：噪音过滤、去重、窗口聚合在 LLM 之前完成，显著降低 token 成本。
4) **分层降级**：LLM/RAG 任一环节出问题，都能回退到“模板化摘要 + 固定 runbook”，保证告警链路不断。
5) **人机协同闭环**：值班同学的反馈进入流中，持续改进检索、规则与提示词。

## 7. 验收标准（可量化、可对齐）

### 7.1 线上指标（效果）

- MTTA（平均确认时间）下降：目标 -30%（对比上线前 2~4 周基线）
- 告警去重后“事件数/告警数”比：告警风暴期减少推送量 ≥ 70%
- 处置建议采纳率：≥ 40%（值班同学点击/执行建议的比例）
- 相似事故召回率：Top5 命中相似事故 ≥ 60%（抽样人工标注）

### 7.2 系统指标（稳定性与成本）

- P0 事件端到端延迟（告警进入 Kafka 到输出工单/卡片）：p95 ≤ 60s
- LLM 调用失败率：≤ 1%（含超时/限流后）
- 峰值成本：单位时间 token 成本可被观测并设置阈值告警
- 全链路可观测：每个事件都有 trace_id，可追溯到检索与生成证据

## 8. MVP 拆解（按 2~3 个迭代落地）

### 迭代 1：事件聚合 + 模板化输出（无 LLM/弱 LLM）

- Kafka 接入告警流
- Flink 去重/聚合，产出 `incident_candidate`
- 输出到工单/IM：以模板化规则生成摘要
- 先把“噪音与统一视图”做出来

### 迭代 2：引入 RAG（runbook/复盘检索）+ 可追溯引用

- 文档流接入（runbook/复盘变更流）
- embedding 入向量库，提供引用链接
- 输出增加“最相关 SOP/相似事故”与证据

### 迭代 3：LLM 作为算子（分类/建议）+ OTel + 降级/Chaos

- vLLM 上线并接入网关
- LLM 输出强约束：结构化 JSON + 引用证据字段
- OTel 全链路埋点与成本监控
- Chaos 演练与降级策略验收

---

## 9. 风险与对策（提前讲清楚）

- 误判风险：强制证据引用 + 置信度 + 人审入口 + 不自动执行高风险操作
- 成本失控：Flink 前置过滤 + 限流 + 小模型优先 + 采样策略 + 成本告警
- 检索质量差：文档分块规范化 + rerank + 版本回滚 + 离线评测集
- 数据合规：对日志/工单做脱敏（PII/密钥），并在流水线中执行
